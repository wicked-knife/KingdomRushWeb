## 结论

确有冗余，但 2035 是断言执行次数，不是 2035 个独立场景。1674 次（82.3%）来自同一个检查循环对每名波次敌人比较出生 tick、类型和路线。应保留全量数据核对，合并报告粒度；真正节省开发时间，需要减少重复模拟、重复加载和与本次改动无关的回归。

主审查对象为 `tests/verify_challenges.gd`；同时核对了战役、存档、地图、塔和原生检查中的相关重叠。`tests/` 当前有 49 个 GDScript 文件，其中 24 个 `verify_*.gd`、13 个含 visual 的脚本，其余含夹具和辅助工具；这些文件数也不能当作独立功能数。

## 不建议删除的检查

- 十个挑战全部配置：现金、生命、波次、路线、布局及模式覆盖；第五关钢铁三个免费箭塔的准确位置与两处营地。它们针对不同数据，不是同一个关卡的重复。
- 禁建与目标模板升级限制、拒绝操作不扣款。界面隐藏按钮与命令拒绝是不同层，两者都需要。
- 三星准入、首次奖励星、重复计分、真实关卡／模式／难度、待结算恢复和失败清除。这些直接涉及用户存档。
- 最后敌人未清不能胜利、孵化与战斗结束的先后关系。这些是真实边界。
- 精灵营地修复／招募／技能／退款和游侠技能。禁止新建兵营与特殊营地是不同规则。
- 二级箭塔与其他二级塔检查不能整文件合并删除：`verify_tower_upgrades.gd` 的交易主循环实际只测兵营、炮塔、法师塔；箭塔主要在 `verify_archer_upgrade.gd`，三级塔又有独立模板和行为。
- 源哈希、图集引用、资源裁剪和发布包初始化。开发目录与隔离 PCK 是不同环境；后者仅交付时运行，不需要每天重跑。
- 备份恢复、未知字段保留、多槽隔离。项目虽然只开放前五关，但统一存档已经保留其他代数据，删掉这些保护并不能直接改善开发效率。

## 高计数掩盖的检查质量问题

这些是收敛检查时要明确的边界，不应靠保留大量重复断言来掩盖。

1. `timeline()` 的预期出生表来自加载后的同一份 definition，能检验模拟器执行是否符合该数据，但不能独自证明导出数据与 Dove 源文件一致。来源哈希核对也不自动证明导出转换完全正确。应保留现有源数据核对证据，并在修改导出逻辑时做源字段差异比对。
2. 禁建测试先调用 `tower_locked()` 决定“哪些塔应该禁止”，再用同一实现检查命令；若某条禁塔配置遗漏，循环可能根本不会测到它。精简时应直接以固定 Dove 禁塔表断言，不能仅依赖被测函数自己给出的禁塔名单。
3. 当前升级循环基本只覆盖建塔后的第一次升级，不能据此宣称所有后续目标模板都已检查。例如第二关钢铁的三级箭塔锁定，应以源锁定表和一个针对性命令拒绝场景覆盖。

## 运行范围建议

- 数据／波次改动：只跑对应关卡的数据核对与时间线；不跑无关塔、全战役回放、全地图及全部原生尺寸。
- 共用命令或模拟机制改动：跑机制代表场景和受影响塔／营地；再按明确风险扩大范围。
- 存档改动：跑统一存档测试和受影响的挑战结算集成。
- UI 改动：Godot 原生只查受影响场景；1024×768 只补布局。截图时重复命中范围／文本适配可按界面状态汇总，不以每个按钮或字串夸大场景数量。
- 完整胜利回放：按用户要求或实证战斗差异按需运行，日常挑战配置验收不默认跑。
- 资源重新裁剪时跑像素／引用核对；交付集中一次导出和隔离 PCK 检查，不因为审查测试而重导出。
